## 3. 零技能归因（v1.7.1）

> 脚本：`scripts/triage_zero_skill.py`（口径直接复用 `scripts/source_health.py::zero_skill_job_ids`，
> 因此下面的 `zeroSkill` 数与报告里的 32.5% / 37.4% 必然一致）。运行约 1.5 秒。

| 源 | 岗位 | 零技能 | 非技术岗 | 疑似词表缺词 | 待人工 | 标题含技术词的零技能 |
|---|---|---|---|---|---|---|
| 快手 `kuaishou` | 1395 | 454（32.5%） | **361（79.5%）** | 50（11.0%） | 43（9.5%） | 30 |
| 小红书 `xiaohongshu` | 1283 | 480（37.4%） | **363（75.6%）** | 79（16.5%） | 38（7.9%） | 47 |

**结论：零技能率高主要是语料构成问题，不是词表缺陷。**

企业官网同时挂技术岗与职能岗（运营 / 产品 / 销售 / 财务 / 税务 / 合规），
这些岗位天然抽不到技术技能。因此：

1. **不调阈值、不改判定口径**——放宽阈值只会掩盖语料构成。
2. **不盲目扩词表**——快手的缺词 token 是 `office / excel / roi / sop / gmv / erp / cad / hrbp`，
   属于业务岗词汇，塞进技术技能表会污染匹配与画像。
3. **真缺口只有一小撮**：小红书 `ios(17) / android(8) / swift(7) / objective-c(5) / sdk(5)`
   合计 40+ 条，值得单独核对词表别名（如 `OC`、`Android 开发`）。
4. **指标改造方向（v1.8.0）**：给岗位加「技术 / 非技术」标签，`source_health` 同时报告
   "技术岗零技能率"，让这个指标变成可行动的信号，而不是长期"关注"。

## 4. 快手发布时间覆盖：根因与修复（v1.7.1）

- **根因**：`src/crawler/kuaishou.py::to_rows()` 把 `publish_time` **写死为空字符串**（社招列表分支），
  只有校招分支读 `releaseTime`。不是数据源缺字段，也不是合并/构建丢字段。
- **修复**：社招改为按 `releaseTime → publishTime → createTime` 顺序取值，统一走
  `src/crawler/util.py::fmt_publish_time`（兼容毫秒时间戳与日期串）；都取不到时保持为空，不编造。
- **回归**：`tests/test_kuaishou.py`（5 条：候选字段、毫秒格式化、缺字段留空、校招可导入）。
- **待验证**：覆盖率提升需要下一次真实抓取才能确认；在此之前 `docs/source_health.md` 的数字**不会变**。


## 5. 美团校招 / 实习接入（v1.7.2）

**结论：接口与解析已就绪并入库，但本轮不并入语料——与社招 JD 重叠 98.4%，净增只有 5 条。**

### 接口事实（2026-11 实测，**无需登录 / cookie / 签名**）

| 项 | 校招 `jobType=1` | 实习 `jobType=2` |
|---|---|---|
| 全站条数 | 198 | 381 |
| `jobDuty` + `jobRequirement` 覆盖 | 100% | 100% |
| `refreshTime`（发布时间）覆盖 | 100% | 100% |
| 技术类条数 | 120 | 191 |
| 丢弃的非技术岗 | 78 | 190 |

> 曾怀疑需要登录态。实测匿名即可，**不需要任何账号 cookie**；
> 与社招一样只需 `u_query_id` / `r_query_id` 这一轮查询 token（整轮复用，换新会让分页退回第 1 页）。

### 为什么没并进语料

`preflight_new_source.py` 体检为 PASS（0 个 id 冲突、0 源内重复、技能覆盖仍 160/161），
但按 `text_hash`（`sha1(jd_clean)`）与现有语料比对后：

| 指标 | 值 |
|---|---|
| 抓到的技术类 | 311 |
| 清洗后唯一 JD | 306 |
| 与现有语料重复 | **301（98.4%），全部来自 `meituan` 社招** |
| 真正新增 | **5** |

即：**美团校招技术岗与社招共用同一套 JD 文本**。并入只会让 `jobs.jsonl` 多 5 行，
却要连带改 `job_freshness.json`、`docs/metrics.md`、`docs/source_health.md`、
`tests/test_dataset_snapshot.py` 常量与 README / memory-bank 的全部数字——成本远大于收益。

**决策**：爬虫、解析与 7 条测试保留入库，但**不注册进构建流水线**——产物只写
`data/raw/meituan_campus_jobs.csv`（gitignored），`data/processed/jobs.jsonl` 保持 5832 条。
理由：一旦注册而数据不并入，任何人本地跑一次爬虫都会让 `test_dataset_snapshot` 失败（实测 5837 ≠ 5832）。
启用时按模块 docstring 里的「3 处注册 + 同步常量」步骤操作。

## 7. 华为数据源现状：不是抓漏，是渠道迁移（v1.8.1 结论，v1.9.0 已解决）

> **v1.9.0 已解决**：新站的岗位列表接口找到了 —— `POST .../recruitmentPosition/pub/getJobPage`
> （`X-HW-ID` + `x-jalor-tenantalias: hcm` + `x-referer` + `x-alb-gray: prod` + `x-language: zh_CN`，
> body `{"curPage":N,"pageSize":10,"jobType":"SR"}`），全站 **578 条 / 58 页**。
> 按技术族过滤后 **288 条**入库（`src/crawler/huawei.py` 已重写，纯 requests，无需登录/账号）。
> 下面保留 v1.8.1 的排查过程，供以后遇到同类"接口枯竭"时参考。

**结论：老门户接口已枯竭（全站 2 条），华为已迁到新站 `career.huawei.com/cn`；校招需登录。**

### 证据（2026-11 实测）

| 检查 | 结果 |
|---|---|
| 老接口 `portalpub/getJob/newHr/page/10/1?jobType=1` | **totalRows = 2**（社招）、`jobType=2` 返回 0 |
| 浏览器打开老门户社招页，看它自己发的请求 | 同一个接口、同样 **2 条** → 不是我们参数错 |
| 新站 `/cn/social-recruitment` 页面文案 | **“共 269 个职位”** |
| 新站 `/cn/campus-recruitment` 页面文案 | 提示需**登录华为账号**后可查看 |
| 51job 第三方通道（仓库中 `huawei_51job.py` 的既有实验） | 9 城市仅 3 条 AI 岗，且无完整 JD |

### 新站接口现状

- 已确认可用：`POST https://apigw-dgg-b0.huawei.com/api/apig/channelhw/recruitmentPosition/pub/calculateSocialRecruitmentJob`
  （`X-HW-ID: app_000000035886`，body `{"jobType":"SR"}`）→ 返回 **175 个类目**，
  字段 `category / categoryName / familyCount / jobFamily / children`。
- **岗位列表接口未暴露**：该页所有 JSON 响应里只有类目树、推荐位、埋点；
  `hcomponent-career-multiPage-search` 等 JS bundle 里也搜不到列表接口路径；
  页面 HTML 为纯前端壳（无 SSR），列表由前端渲染。

### 因此华为接入有三条路（按成本排序）

1. **浏览器渲染抓取**（无需账号）：打开社招页 → 点类目 → 读渲染后的岗位卡片与详情页。
   能拿到 269 条，但慢（每条约 1-2 秒）且依赖 DOM 结构。
2. **继续逆向新站列表接口**：需要再花时间观察点击类目后的 XHR（本次未捕获到），不确定能否成功。
3. **用账号登录校招站**：校招岗位必须登录才可见；账号对**社招无帮助**（社招本来就公开）。

### 复现要点

- 老接口是否枯竭：`GET .../getJob/newHr/page/10/1?curPage=1&pageSize=20&jobType=1&searchType=1` → 看 `pageVO.totalRows`
- 新站类目：`POST .../calculateSocialRecruitmentJob` with `{"jobType":"SR"}` + `X-HW-ID` 头
- 新站是否 SSR：抓 `/cn/social-recruitment` HTML，搜岗位标题（本次只有占位文案，无列表数据）

> 在拿到新站列表接口或改用渲染抓取之前，`huawei` 源会一直是 2 条 / 发布覆盖 0%；
> `docs/source_health.md` 里它的「⚠️ 关注」是**渠道迁移**导致，不是抽取器问题。


## 8. 接口"枯竭"先查是否迁站（v1.9.0）

**事件**：华为源长期只有 2 条，第一反应是"抓漏 / 参数错"。
实测发现老接口 `portalpub/getJob/newHr` 确实只剩 2 条，但**华为已迁到新站**
`career.huawei.com/cn`——那里有 578 条社招岗位。

**规则**：
1. 先确认"接口返回的总数"（`totalRows`），别只数自己抓到几条；
2. 用浏览器打开页面，看**它自己**发的请求——与爬虫一致才算接口没变；
3. 找页面上的"体验新版 / 查看全部"入口，往往指向迁移后的站点；
4. 新版站点若是前端渲染，优先从**内联配置**（如 `comData` 的 `moreInfo.url`）找路由，
   再抓该页 XHR 找列表接口；实在拿不到再退回 DOM 抓取。

**同类坑**：页面上的"共 269 个职位"是**某个类目**的数量，不是全站（全站 578）。
