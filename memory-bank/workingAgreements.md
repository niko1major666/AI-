# 上下文与输出预算执行规则（Working Agreements）

> 目的：在保证正确性的前提下，控制单次会话的上下文与输出体积，避免长会话导致注意力稀释、关键口径丢失、响应变慢。
> 适用：本仓库所有 Cline 会话；与 `.clinerules/memory-bank.md` 配合使用。
> 原则：**先固化、再压缩；宁可分页，不可臆测**。不为省 token 牺牲安全、测试口径与关键决策。

## 1. 事实边界

- 模型上下文窗口、自动压缩（auto-compact）阈值由客户端/模型配置决定，不在代码里硬改。
- 可控制的是四件事：每次读多少、命令输出多少、回复多长、何时把记忆落盘。

## 2. 读取预算

| 场景 | 规则 |
|---|---|
| 单文件 | 单次 ≤ 400 行；超过必须用 `start_line` / `end_line` 分页（如 `src/app/app.py` 约 930 行） |
| 多文件并行 | 一轮总读取 ≤ 1500 行；优先只读相关章节，不整目录扫描 |
| 已知位置 | 先用 `search_codebase` / `Select-String` 定位，禁止「先整文件读完再找」 |
| 命令输出 | 加过滤：`Select-Object -Last N`、`Select-String`、`git --no-pager diff --stat`；不把完整 diff / 日志 / 爬虫输出灌入上下文 |
| 重复读取 | 同一文件不重复整读；复核只读改动区间 |
| 外部网页 | 只取所需段落，不整页长文回灌 |

## 3. 输出预算

- 代码与文档**先落盘**再汇报，回复只给路径 + 关键片段，不贴整文件。
- 单次回复按「结论 → 改动 → 验证 → 风险/下一步」组织，不复述工具输出。
- 大批量修改合并成批完成，减少来回轮次。
- 长日志只摘关键行（失败用例、数字、错误码）。

## 4. 记忆固化（优先级最高）

触发点（满足任一）：

1. 完成一个可交付里程碑（功能 / 修复 / 发版 / 数据接入）；
2. 准备提交或推送前；
3. 上下文使用约 60–70%；
4. 任务即将切换（开发 → CI 排查 → 发版）；
5. 发现新的口径、坑或决策。

落盘位置：

| 内容 | 文件 |
|---|---|
| 当前状态与下一步 | `memory-bank/activeContext.md` |
| 已完成事项与量化指标 | `memory-bank/progress.md` |
| 技术决策与实现模式 | `memory-bank/systemPatterns.md` |
| 技术栈 / 命令 / 约束 | `memory-bank/techContext.md` |
| 数据接入 SOP | `memory-bank/dataOnboarding.md` |

要求：写清「结论 + 数字 + 文件路径 + 下一步」；测试数、语料规模、指标只认 `docs/metrics.md` 与 memory-bank，不依赖对话记忆。

## 5. 新会话交接

- 完成里程碑并提交后，优先新开会话；开场只读 memory-bank 全部文件 + `git log -1`，不回放长对话。
- 需要历史细节时按主题读对应文档（如数据问题读 `dataOnboarding.md`，UI 问题读 `systemPatterns.md`），不整目录扫描。
- 新会话接手后先确认：当前分支、HEAD、工作区是否干净、测试是否通过。

## 6. 例外（不得为省预算牺牲）

- 安全、密钥、权限相关；
- 测试基线、语料口径、版本元数据（如测试数、语料规模、`docs/metrics.md`）；
- 数据删除 / 覆盖 / 迁移等不可逆操作；
- 用户明确要求「完整检查 / 全量读取」。

## 7. 每次任务自检

- 开始：目标是什么？需要哪些文件/章节？预计读多少行？
- 结束：测试跑了吗？相关数字更新了吗？memory-bank 更新了吗？提交/推送了吗？
