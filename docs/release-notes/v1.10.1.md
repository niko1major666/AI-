# v1.10.1 自动化维护链路 + 排除清单收敛修复

把「研发 → 排查 → 修补 → 验证 → 发布」做成一条可重复执行的流水线，并用它跑出了一轮收敛。

## 新增：`agent-team/pipeline.mjs`

```bash
node pipeline.mjs --config goals/xxx.json --audit-only      # 只体检，不改任何东西
node pipeline.mjs --config goals/xxx.json                  # 体检 + 数据修补 + 门禁验证
node pipeline.mjs --config goals/xxx.json --with-agents     # 额外跑 LLM 代码修复任务
node pipeline.mjs --config goals/xxx.json --release patch   # 全绿后提交/打 tag/推送
```

| 阶段 | 做什么 | 失败处理 |
|---|---|---|
| 1 体检 | 仓库扫描（硬编码/密钥/杂物）+ 语料审计（非技术/未知/零技能） | 只报告 |
| 2 决策 | 把发现映射成动作（数据修补 / 代码任务 / 无需处理） | 无动作则跳过 |
| 3 修补 | 数据：重算排除清单 → 重建语料 → 重生成 docs；代码：交给 agent-team | 失败即停 |
| 4 验证 | 10 项门禁（`run.mjs --gates-only`） | 红则停，不发布 |
| 5 发布 | 版本号 + commit + tag + push（**默认关闭**） | 需显式 `--release` |

设计要点：每阶段可单独跑；重活全在子窗口（主窗只收摘要）；发布必须显式授权。

## 修复：排除清单必须累积

流水线首次运行时踩到的坑：`apply-relevance.py` 从**当前（已过滤）语料**重算清单，
于是覆盖了原有 1607 条 → 下一次 merge 把它们全放回来（语料从 4557 弹回 6098，门禁立红）。

修复：清单改为**只增不减的并集**（`existing | newly_classified`），并记录
`newlyExcluded / carriedOver` 便于审计。清单现在 **1669 条**。

第二轮补清的 56 条，是首轮剔除后**去重顺序变化**才浮出来的（此前被重复行挤掉）。
说明「剔除 → 重建 → 复查」至少要跑两轮才能收敛——这正是流水线要自动化的原因。
