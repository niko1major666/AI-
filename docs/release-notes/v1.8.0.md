# v1.8.0 技术岗 / 非技术岗分层：零技能率不再是噪音

v1.7.1 的归因结论（零技能岗位里 79.5% 是职能岗）从"一次性分析脚本"升级为**常规指标**：
`source_health` 现在同时报告「总零技能率」和「技术岗零技能率」。

**结论先行**：快手 32.5% → **4.6%**、小红书 37.4% → **8.3%**。
之前被标「⚠️ 关注」的两个源，技术岗其实完全健康；异常来自它们同时挂着运营/产品/销售岗。

## 新增

### 岗位族判定（`src/data/job_family.py`）
- `classify_title(title)` → `tech` / `non_tech` / `unknown`，纯函数、无依赖。
- **技术标记优先**：标题含「工程师/开发/算法/架构/大数据/SRE…」即为技术岗，
  避免「产品研发工程师」被「产品」误判成职能岗。
- `unknown`（如「管培生」）不计入技术岗分母，避免把模糊岗位硬塞进任一侧。

### 来源健康新增「技术岗零技能」列
- 总览新增一行：技术岗零技能 `219 条 / 3446 条（6.4%）`。
- 分来源表格新增一列，同时保留原来的「零技能」总口径。
- 判定口径里写明：**状态判定仍按总零技能率，阈值未改**。

## 为什么先不改状态阈值

把「⚠️ 关注」直接改成按技术岗零技能率判定，会让快手/小红书立刻变「✅ 正常」——
这是**指标口径变更**，会改变所有人对这两源的既有认知。本次只加列、不改判定，
把决策权留给维护者；需要切换时改 `src/data/source_health.py` 里的 `status` 计算一处即可。

## 验证
- 测试 **335 → 350**（新增 `tests/test_job_family.py`：15 条分类用例，含技术标记优先与 unknown 边界）。
- 门禁 10 项全绿；`docs/metrics.md` 零 diff（语料未变）；
  `docs/source_health.md` 有预期变更（新增列 + 总览一行），由脚本重跑生成。
- 未改：判定阈值、`skill_taxonomy.yaml`、`jobs.jsonl` 字段与语义、隐私与上传限制。

## 已知限制
- 标题判定是启发式：`研发管理`、`技术运营` 这类复合岗会归到 `tech` 或 `unknown`，
  属解释性指标，不适合做强断言（测试只锁明确用例）。
- 技术岗分母为 0 的源（如全部是职能岗的小源）该列显示 `-`，不参与汇总。
